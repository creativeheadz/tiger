%fire001w
Nothing in the kernel's packet filter drops incoming IPv4 traffic that no
rule has accepted: every chain on the input hook, in nftables and in
legacy iptables, has the policy accept and does not end with an
unconditional drop or reject. Every service listening on an address
reachable from the network is then reachable, including ones started by
accident, by a package, or by a user, and a service's own access rules
are the only defence.

The detail lists the input chains that were found, if any. Rules that
drop only some traffic (one port, one source) do not change this: what
matters is what happens to a packet that nothing matched.

To fix it, use the firewall front end the distribution provides, which
sets a default-deny policy and lets the services you name through:
'ufw enable' on Ubuntu and Debian (after 'ufw allow ssh' on a remote
machine), 'systemctl enable --now firewalld' on Fedora, RHEL and SUSE.
With nftables directly, a chain such as:

    table inet filter {
      chain input {
        type filter hook input priority filter; policy drop;
        ct state established,related accept
        iif "lo" accept
        tcp dport 22 accept
      }
    }

in /etc/nftables.conf, loaded by 'systemctl enable --now nftables'.

Ports that Docker publishes are forwarded before they reach the input
chain, so they bypass this policy; restrict them with Docker's own
DOCKER-USER chain.
%fire002w
As fire001w, for IPv6. A host can deny IPv4 by default and leave IPv6
open: an nftables table of family 'ip' or an iptables (not ip6tables)
policy covers IPv4 only. If the host has IPv6 addresses, its services
are reachable over IPv6 even when IPv4 is filtered. Use a table of
family 'inet', which covers both, or set the ip6tables policy too. If the
host does not use IPv6 at all, it can be switched off with
net.ipv6.conf.all.disable_ipv6 = 1, and this check then says nothing
about it.
%fire003i
Incoming traffic of this family is denied by default: the chain named
drops or rejects what its rules do not accept. This is informational;
it says nothing about which services the rules let through, which is
worth reviewing with 'nft list ruleset' (or 'ufw status verbose',
'firewall-cmd --list-all').
%fire004e
The packet filter rules could not be read, so the check cannot say
whether incoming traffic is filtered. Reading them needs root ('nft list
ruleset' fails with "Operation not permitted" otherwise), and the nft or
iptables command. The detail gives the command's own error.
